ai-assisted development

why i don't completely trust ai-generated code

ai coding tools can make development much faster — but when an implementation starts drifting from the original requirement, knowing when to stop matters just as much as knowing what to prompt.

ai coding tools can be incredibly useful.

the appeal is obvious: tasks that used to take significantly longer can sometimes be completed much faster, and an ai agent can help you write code, debug problems, understand an unfamiliar codebase, or get an idea off the ground.

but faster doesn't always mean better.

as i've worked with ai-assisted development, i've noticed a recurring problem: an ai agent doesn't always understand what you're actually trying to accomplish.

it might understand the code in front of it. it might understand the prompt you gave it. but that doesn't necessarily mean it understands the business logic behind a requirement, the context surrounding it, or why you chose a particular approach in the first place.

and that's where things can start to drift.

when a simple task stops being simple

one behavior i've noticed with ai coding tools is their tendency to overengineer.

you might start with a relatively simple requirement. the agent proposes a solution, you test it, and something doesn't work quite right.

so you ask it to fix the problem.

it makes another change.

that change introduces another issue, so you ask it to fix that too.

after a few rounds of this, you can end up surprisingly far away from the problem you originally wanted to solve.

instead of stopping to question an earlier assumption, the agent may continue trying to make the current implementation work. more state gets introduced. more conditions appear. logic that wasn't part of the original requirement starts creeping in.

eventually, you aren't really solving the original problem anymore. you're solving problems created by the previous solutions.

that's usually my signal to stop.

a small example

let's start with a deliberately simple requirement:

disable a submit button while a request is running, then re-enable it when the request finishes.

we really only need one piece of state: 

let isSubmitting = false;

async function submitForm() {
  if (isSubmitting) return;

  isSubmitting = true;
  updateButton();

  try {
    await fakeRequest();
    console.log("submitted successfully");
  } catch (error) {
    console.error("submission failed", error);
  } finally {
    isSubmitting = false;
    updateButton();
  }
}

isSubmitting represents exactly what we need to know. while the request is running, it's true. when the request finishes — whether it succeeds or fails — the finally block resets it.

now imagine that the first implementation doesn't behave quite how we expect.

we ask an ai agent to fix it. then we ask it to handle another issue. then another.

instead of returning to the original requirement, each new change builds on the previous implementation.

eventually, our simple submission state might start looking something like this: 

let isSubmitting = false;
let requestFailed = false;
let retryCount = 0;
let buttonDisabled = false;

async function submitForm() {
  if (buttonDisabled) return;

  isSubmitting = true;
  buttonDisabled = true;
  updateButton();

  try {
    await fakeRequest();

    requestFailed = false;
    retryCount = 0;
  } catch (error) {
    requestFailed = true;
    retryCount++;

    if (retryCount < 3) {
      buttonDisabled = false;
    }

    console.error("submission failed", error);
  }

  if (!requestFailed) {
    isSubmitting = false;
  }

  if (requestFailed && retryCount >= 3) {
    buttonDisabled = false;
    isSubmitting = false;
  }

  updateButton();
}

now we're keeping track of four different pieces of state:

  • isSubmitting
  • requestFailed
  • retryCount
  • buttonDisabled

we've also introduced retry behavior that wasn't part of the requirement.

the code isn't necessarily more sophisticated because it's longer. we've just accumulated logic while trying to fix each new problem individually.

this is the kind of moment where i think it's important for the developer to interrupt the loop.

stop and go back to the requirement

when i notice this happening, one of the most useful things i can do is stop looking at the latest error for a moment and re-read the original requirement.

what am i actually trying to accomplish?

what is the simplest behavior the code needs to support?

which parts of the current implementation are actually necessary?

in our example, the requirement hasn't changed.

we still just need to know whether the request is currently running.

so instead of asking the agent for another fix, we can remove the unnecessary state and return to something much simpler: 

let isSubmitting = false;

async function submitForm() {
  if (isSubmitting) return;

  isSubmitting = true;
  updateButton();

  try {
    await fakeRequest();
    console.log("submitted successfully");
  } catch (error) {
    console.error("submission failed", error);
  } finally {
    isSubmitting = false;
    updateButton();
  }
}

sometimes recovering from ai drift doesn't require a better prompt or another generated solution.

sometimes it means recognizing that we've gone in the wrong direction and simplifying.

give the agent direction

another thing i've found helpful is not always asking the ai agent to figure everything out from scratch.

if i already have an idea of how something should be structured, i can give it that structure.

that might mean providing:

  • a small code skeleton
  • constraints the implementation needs to follow
  • existing patterns it should preserve
  • the expected behavior
  • things it explicitly should not change

this gives the agent a clearer direction instead of leaving it to make assumptions about what i want.

and when an agent does make an assumption, i think it's important to catch it early.

otherwise, you can end up in an endless back-and-forth where each prompt is trying to correct the result of the previous prompt.

knowing when to stop prompting

i think this is one of the more important skills when coding with ai.

when something isn't working, the instinct can be to immediately send another prompt:

"that didn't work. fix it."

and then:

"now this is broken."

and then:

"go back and fix this too."

but there comes a point where another prompt isn't necessarily the most productive next step.

some signals i watch for are:

  • the same files are being modified repeatedly without resolving the problem
  • each fix introduces another issue
  • the implementation is becoming much more complicated than the requirement
  • new behavior is being added that i never asked for
  • the agent is making assumptions about how the system should work
  • i'm spending more time correcting generated code than understanding or solving the original problem

when that happens, i'd rather stop, inspect the current state myself, and decide what should actually stay.

ai still needs an engineer

none of this makes me less interested in ai-assisted development.

i use these tools because they're useful.

they can accelerate repetitive work, help explore unfamiliar code, suggest implementations, explain errors, and make it much faster to iterate on an idea.

but i don't think the developer's role disappears when an ai agent starts writing the code.

if anything, judgment becomes more important.

someone still needs to understand the requirement.

someone still needs to recognize when the implementation is becoming unnecessarily complicated.

someone still needs to question the assumptions being made.

and someone still needs to know when it's time to stop generating and change direction.

for me, the best way to use ai coding tools isn't to hand over the entire development process. it's to treat them as a very capable collaborator — one that can move quickly, but still needs direction.

ai can generate a lot of possible answers very quickly.
the developer still has to decide whether we're solving the right problem.
